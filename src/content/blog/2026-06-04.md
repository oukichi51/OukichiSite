## 作業配分モデル

作業量を人員や期間に割り振るためのモデル

### 基本式

```text
(工数) = (人数) × (期間)
```

### 具体的な問題のメモ

228日で57%の作業が完了。現在の作業も5.5%は終了。あと何日かかるか計算する問題。
まず、全体の日数を求める。
```text
(全体) = 228 ÷ 0.57 = 400(日)
```
今、62.5%の作業が完了しているので、残りの37.5%が終わる期間を求めればいい。
```text
(残りの日数) = 400 × 0.375 = 150(日)
```

## EVM(Earned Value Management)

コストとスケジュールの2つを定量的に管理する進捗管理方法。

### 基本の3要素


| 略語 | 意味 | 説明 |
|---|---|---|
| **PV** | Planned Value | 計画上、現時点までに完了しているはずの作業量・予算 |
| **EV** | Earned Value | 実際に完了した作業の価値・出来高 |
| **AC** | Actual Cost | 実際にかかったコスト |

### 重要な式

```text
SV = EV − PV
```
SVはスケジュール差異。  
0より大きければ予定より進んでおり、0より小さければ予定より遅れている。

```text
CV = EV − AC
```
CVはコスト差異。  
0より大きければ予算内、0より小さければ予算超過である。

```text
SPI = EV ÷ PV
```

SPIはスケジュール効率指数。  
1より大きければ予定より進んでおり、1より小さければ遅れている。

```text
CPI = EV ÷ AC
```

CPIはコスト効率指数。  
1より大きければコスト効率が良く、1より小さければコスト効率が悪い。

## ソフトウェア開発の見積り手法

ソフトウェア開発では、開発に必要な**工数・期間・費用**を見積もるために、開発規模を定量的に把握することが重要です。

### パラメトリック見積もり(係数見積もり)

情報システム開発やソフトウェア開発などのコストや工数を見積もる手法の一つで、過去のデータから得られた経験則に基づいて、計測可能な値を集計して見積もりを行う手法。

代表的な見積り手法には、**COCOMO**、**ファンクションポイント法**、**プログラムステップ法**があります。

**COCOMO**は、ソフトウェアの規模をもとに開発工数を見積もるモデルです。  
COCOMOは **Constructive Cost Model** の略で、主にソースコード行数を表す **KLOC** を使って工数を算出します。

```text
工数 = a × (KLOC)^b
```

ここで、**KLOC** は1,000行単位のソースコード行数を表します。  
**a** や **b** は、プロジェクトの種類や特性によって決まる係数です。

COCOMOは、過去の開発実績やコード規模をもとに、数式で工数を見積もれる点が特徴です。  
ただし、開発前にソースコード行数を予測する必要があるため、要件があいまいな初期段階では精度が下がりやすいという注意点があります。

**ファンクションポイント法**は、ソースコード行数ではなく、利用者から見た**機能の数や複雑さ**をもとに開発規模を見積もる方法です。

ファンクションポイント法では、システムの機能を次のように分類して評価します。

| 分類 | 内容 |
|---|---|
| 外部入力 | 画面やファイルからデータを入力する機能 |
| 外部出力 | 帳票や画面にデータを出力する機能 |
| 外部照会 | 検索や問い合わせを行う機能 |
| 内部論理ファイル | システム内部で管理するデータ |
| 外部インタフェースファイル | 他システムと共有・参照するデータ |

これらの機能に対して、複雑さに応じた点数を付け、ソフトウェア全体の規模を算出します。  
この点数を**ファンクションポイント**と呼びます。

ファンクションポイント法は、利用者視点で機能量を評価するため、開発言語や実装方法に左右されにくい点がメリットです。  
そのため、要件定義や設計の段階でも見積もりやすい手法です。  
一方で、機能の分類や複雑さの判断には経験が必要で、評価者によって結果がばらつくことがあります。

**プログラムステップ法**は、ソフトウェアの規模を**プログラムの行数**で見積もる方法です。  
ここでいうプログラムステップとは、ソースコードの命令行数のことです。

プログラムステップ法では、作成するプログラムが何行程度になるかを予測し、その行数をもとに工数や費用を見積もります。

```text
予想ステップ数 × 1ステップあたりの開発単価 = 開発費用
```

または、次のように必要工数を求めることもあります。

```text
予想ステップ数 ÷ 1人月あたりの生産性 = 必要工数
```

たとえば、予想ステップ数が20,000ステップで、生産性が1人月あたり2,000ステップの場合、必要工数は次のようになります。

```text
20,000 ÷ 2,000 = 10人月
```

つまり、開発には約10人月が必要と見積もれます。

プログラムステップ法は、考え方がシンプルで、過去の開発実績と比較しやすい点がメリットです。  
ただし、開発言語やフレームワーク、自動生成コード、ライブラリ利用の影響を受けやすく、コード行数が多いほど価値が高いとは限らない点に注意が必要です。

3つの手法の違いは、次のように整理できます。

| 手法 | 見積りの基準 | 特徴 |
|---|---|---|
| COCOMO | KLOC、コスト要因 | コード規模から工数を数式で見積もる |
| ファンクションポイント法 | 利用者から見た機能量 | 開発言語に依存しにくい |
| プログラムステップ法 | ソースコード行数 | シンプルだが言語や実装方法の影響を受けやすい |

まとめると、**COCOMO**はコード規模をもとに工数を数式で見積もる方法、**ファンクションポイント法**は利用者から見た機能量で見積もる方法、**プログラムステップ法**はプログラム行数で見積もる方法です。

開発初期で機能量から見積もりたい場合はファンクションポイント法、過去のコード行数データがある場合はCOCOMOやプログラムステップ法が向いています。

## プログラムステップ数での全体の生産性の求め方

全体の生産性は、基本的に次の式で求めます。

```text
全体の生産性 = 全体のステップ数 ÷ 全体の工数
```

たとえば、作業全体のステップ数を **N** とします。

工程ごとの生産性が次のように与えられているとします。

```text
X, Y, Z（ステップ/人月）
```

このとき、各工程の作業量をそれぞれ **A, B, C** とすると、全体のステップ数 **N** は次のようになります。

```text
N = A + B + C
```

各工程に必要な工数は、次のように求めます。

```text
工程Aの工数 = A / X
工程Bの工数 = B / Y
工程Cの工数 = C / Z
```

そのため、全体の工数は次のようになります。

```text
全体の工数 = A/X + B/Y + C/Z
```

全体の生産性は、全体のステップ数を全体の工数で割って求めるので、次のようになります。

```text
全体の生産性 = N ÷ (A/X + B/Y + C/Z)
```

また、**N = A + B + C** なので、次のようにも表せます。

```text
全体の生産性 = (A + B + C) / (A/X + B/Y + C/Z)
```

工程ごとの作業量の割合がわかっている場合は、その割合を使います。

たとえば、各工程の作業量を次のように表します。

```text
A = aN
B = bN
C = cN
```

このとき、**a + b + c = 1** です。

全体の生産性は次のようになります。

```text
全体の生産性 = N ÷ (aN/X + bN/Y + cN/Z)
```

ここで、分子と分母に共通して **N** があるため、約分できます。

```text
全体の生産性 = 1 ÷ (a/X + b/Y + c/Z)
```

つまり、作業全体を **N** として考えても、最終的には **N** は消えます。

重要なのは、単純に次のような平均を使わないことです。

```text
(X + Y + Z) ÷ 3
```

生産性は **ステップ/人月** なので、全体の生産性を求めるには、まず全体の工数を考える必要があります。

まとめると、全体の生産性は次の式で考えます。

```text
全体の生産性 = 全体のステップ数 ÷ 全体の工数
```

工程ごとの作業量が異なる場合は、各工程の作業量と生産性を使って、次のように求めます。

```text
全体の生産性 = (A + B + C) / (A/X + B/Y + C/Z)
```

また、3が出てくるのは、3つの工程の作業量がすべて同じ場合だけです。  
作業量が同じとは限らない場合は、3で割る平均ではなく、各工程の作業量を使って計算します。

## コロケーションとは

**コロケーション**とは、プロジェクトメンバーを同じ場所に集めて作業させることです。

プロジェクトマネジメントでは、チームメンバー同士のコミュニケーションを円滑にし、情報共有や意思決定を早くするために行われます。

たとえば、開発者、設計者、テスター、プロジェクトマネージャーなどが、同じ部屋や同じフロアで作業するような形です。

コロケーションの目的は、メンバー間の距離を近くして、必要な情報をすぐにやり取りできるようにすることです。

通常、プロジェクトでは、メールやチャット、会議などを使って情報共有を行います。  
しかし、メンバーが離れた場所で作業していると、確認に時間がかかったり、認識のずれが起きたりすることがあります。

コロケーションを行うと、疑問点や問題が発生したときに、その場ですぐに相談できます。  
そのため、コミュニケーションの遅れを減らし、作業を進めやすくなります。

コロケーションには、次のようなメリットがあります。

| メリット | 内容 |
|---|---|
| コミュニケーションが取りやすい | 近くにいるため、すぐに相談や確認ができる |
| 意思決定が早くなる | 関係者が同じ場所にいるため、判断や調整がしやすい |
| 認識のずれを防ぎやすい | 直接話すことで、誤解や伝達ミスを減らせる |
| チームワークが高まりやすい | 一緒に作業することで、メンバー間の一体感が生まれる |
| 問題への対応が早くなる | トラブルが起きたときに、すぐに関係者で対応できる |


## 定常業務

常設の組織形態の下で、決められた作業を反復して行う業務のこと。

## コンティジェンシー計画

災害や事故、システム障害などの非常事態が発生した場合に備え、被害を最小限に抑えながら事業や業務を継続・復旧するための対応手順や体制を事前に定めた計画のこと。

## 構成管理(コンフィギュレーション・マネジメント)

対象の構成要素を把握し、その状態や設定、変更などを体系的に記録、管理すること。IT分野では情報システムやネットワーク、ソフトウェアなどの要素を把握、管理する仕組みや活動をこのように呼ぶ。

## 管理図

工程の状態や品質を時系列で表した図であり、工程が安定した状態かどうかを判断するために使用されます。一般的には中央線と上方管理限界と下方管理限界を示す線を引いた図に、製品などの特性値を定期的に記録していくことで、品質不良や工程の以上を検出し、不良原因の除去や再発防止に役立出ます。
